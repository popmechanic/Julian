# TinyBase 9.2.0 → 9.5.1: what changed, and what applies to this house

Researched 2026-08-27 against primary sources: the GitHub releases, the npm
registry, the shipped package contents of both versions, and empirical repros
run against locally installed copies of 9.2.0 and 9.5.1. Repro scripts lived in
the session scratchpad (`repro53.mjs`, `repro53b.mjs`, `reserved.mjs`); their
essential logic is quoted inline below so the results stay reproducible.

This repo pins `tinybase ^9.2.0` in `app/`, `shared/`, and `sync/`
(`app/package.json`, `shared/package.json`, `sync/package.json`), with 9.2.0
actually installed in each workspace's `node_modules`. The **root**
`package.json` pins `^9.3.0` and the root `bun.lock` resolves `tinybase@9.3.0`
— the workspaces and the root are already on different minors today.

---

## 1. The releases between 9.2.0 and 9.5.1

From the npm registry (`https://registry.npmjs.org/tinybase`, `time` field) —
the complete list of stable releases in the interval, with no patch releases
between the minors:

| Version | Published (npm) | GitHub release |
|---|---|---|
| 9.2.0 | 2026-07-11 | [v9.2.0](https://github.com/tinyplex/tinybase/releases/tag/v9.2.0) |
| 9.3.0 | 2026-07-27 | [v9.3.0](https://github.com/tinyplex/tinybase/releases/tag/v9.3.0) |
| 9.4.0 | 2026-08-08 | [v9.4.0](https://github.com/tinyplex/tinybase/releases/tag/v9.4.0) |
| 9.5.0 | 2026-08-15 02:45Z | **none** — the API answers 404 for tag v9.5.0 |
| 9.5.1 | 2026-08-15 10:13Z | [v9.5.1](https://github.com/tinyplex/tinybase/releases/tag/v9.5.1) |

9.5.0 and 9.5.1 are the same feature release: 9.5.1 followed 9.5.0 by 7.5
hours, the v9.5.1 GitHub release carries the whole "v9.5" changelog, and the
`releases.md` shipped inside the 9.5.1 package has a single `v9.5` section
matching it. There is no separate v9.5.0 GitHub release to cite. (A
9.6.0-beta.1 exists — 2026-08-19 — outside this report's range; see §7.)

### v9.3.0 — the big one ([release notes](https://github.com/tinyplex/tinybase/releases/tag/v9.3.0))

Headline: multiple WsSynchronizers can share one physical WebSocket via a
`channelId` third argument and the `tinybase` subprotocol. Explicitly:
"WsServerDurableObject continues to use one URL path and Durable Object per
WebSocket" — so multiplexing does not change the DO server this repo runs.
Also a very large reliability/hardening batch, the parts of which that matter
here are cited throughout §§2–6. Its "breaking-ish" list: numeric error codes,
failed-transaction rollback, rejection of previously accepted reserved or
unserializable values, client-only Solid/Svelte exports, Solid accessor
changes, Svelte export cleanup.

### v9.4.0 ([release notes](https://github.com/tinyplex/tinybase/releases/tag/v9.4.0))

Headline: `selectAll` keyword for queries (select every cell of a root or
joined row, heterogeneous rows supported). Hardening: multiplex channel caps
(100 channels, 1,024-byte channel ids), `startAutoPersisting` rollback on
half-failure, and one DO-relevant line quoted in full in §5.

### v9.5.0 / v9.5.1 ([release notes](https://github.com/tinyplex/tinybase/releases/tag/v9.5.1))

Headline: **schema enums** (`{enum: [...]}` in cell/value schemas, issue
tinyplex#38) and **schema type unions** (`{type: ['string','number']}`, issue
tinyplex#223), plus type-level-only fixes to the `/with-schemas` surface
(schematizer factories exported as values, `ResultCell` widened to `Cell`,
`Send`/`Receive` `requestId` typed `IdOrNull`). "These are type-level fixes
only, and require no changes to your runtime code."

## 2. The fragmenter (issue behind `FRAGMENT_SIZE`)

**Confirmed: 9.2.0's fragmenter is the lossy regex; 9.3.0 replaced it; nothing
further changed the algorithm through 9.5.1.**

- 9.2.0, from the installed dist
  (`app/node_modules/tinybase/synchronizers/synchronizer-ws-client/index.js`):
  fragments are produced with `new RegExp(`.{1,${maxFragmentSize}}`, 'g')`.
  JavaScript's `.` (without the `s` flag) does not match U+2028/U+2029 (or
  \n/\r), and `JSON.stringify` emits U+2028/U+2029 raw — so any record content
  containing those code points was silently deleted in transit whenever the
  payload was large enough to fragment.
- 9.3.0 release notes: "WebSocket fragments now split by UTF-8 byte size at
  code-point boundaries and use at most 1,000 fragments."
- 9.5.1 dist confirms the implementation: a surrogate-pair-aware code-point
  walk accumulating `getWebSocketPayloadSize(codePoint)` (UTF-8 bytes) against
  `maxFragmentSize`, with `MAX_FRAGMENT_COUNT = 1e3` and — new receiving-side
  bounds — `MAX_WEBSOCKET_BUFFER_SIZE = 16777216` (16 MiB) per complete
  message, `MAX_FRAGMENT_BUFFERS = 100`, `MAX_PENDING_REQUESTS = 100`
  (constants read from
  `tinybase@9.5.1/synchronizers/synchronizer-ws-client/index.js`).
- 9.4.0 adjusted only the *limits*, not the algorithm: "Fragment and
  startup-buffer limits are shared across the physical socket" (v9.4.0 notes).

**Semantics change for our `FRAGMENT_SIZE = 262144`** (`app/src/lib/store.ts:10`,
`sync/src/do.ts:167`): in 9.2.0 the parameter counted UTF-16 code units (the
9.2.0 typedoc says only "An optional maximum size"), so 256Ki *characters*
could serialize to ~1 MiB of UTF-8 — right at Cloudflare's cap the constant
exists to avoid. The 9.5.1 typedoc
(`@types/synchronizers/synchronizer-ws-client/index.d.ts`) now reads: "An
optional target maximum UTF-8 byte size for each WebSocket message fragment.
Unicode code points are never split and can exceed this size. TinyBase sends at
most 1,000 fragments for one payload, increasing the target when needed." So
after the bump, 262144 means 256 KiB of actual wire bytes — the constant
becomes *more* correct, no change needed.

**New watch item**: the 16 MiB complete-message cap (9.3.0: "complete messages
and multiplex envelopes are limited to 16 MiB, with oversize input closing only
its sender") is new. Initial sync sends the store's full content as one logical
message; the per-cell 64 KiB guard bounds cells, not the record. If the life
record ever approaches 16 MiB of serialized content, first-sync would start
failing with the peer closed (error 15 / status 1013). Not close today, but it
is now a hard ceiling that did not exist under 9.2.0.

## 3. Issue #53 (createMiddleware flattens setMergeableContent stamps): NOT fixed

**Empirically reproduced on 9.5.1 — the hazard is unchanged.** No release note
between 9.3.0 and 9.5.1 mentions it, and the v9.3.0 middleware work
("Middleware receives cloned object and array values in public JavaScript
form, with callback results validated and encoded only at the Store boundary";
"Middleware and Checkpoints now clean up Store registrations safely…") does not
cure it.

Repro (run with `bun` against both installed versions; scratchpad
`repro53.mjs` / `repro53b.mjs`): create a source MergeableStore with schema
`{messages: {text: {type:'string'}, content: {type:'array'}}}`, write rows
(one deleted), take `getMergeableContent()`; on a destination store with the
same schema, call `createMiddleware(dst)` (no callbacks) and then
`setMergeableContent(content)`; compare stamp trees.

| Case | 9.2.0 | 9.5.1 |
|---|---|---|
| unwrapped store, array-carrying content | faithful | faithful |
| wrapped store, string-only content | faithful | faithful |
| wrapped store, array-carrying content | **flattened** | **flattened** |

The failure shape is exactly #53's: with an array-typed cell present, every
live stamp in the affected rows (the string cells too, as collateral of the
same transaction) is rewritten under the destination store's own client id and
fresh HLCs; deletion stamps keep their original HLCs. Consequences:

- The lazy-guards architecture in `sync/src/do.ts` (`ensureGuards`, guards
  installed only at the first live-traffic surface, restore refusing a wrapped
  store) **must survive the bump unchanged**.
- The pinned fixture in `sync/test/restore.test.ts` (`makeSourceExport`'s
  `content` array cell) stays load-bearing.
- The upstream report contemplated in #53 is still worth filing — the bug is
  live in latest.

## 4. Stamp/HLC format, wire protocol, and the export codec

**The wire convention `shared/export-codec.ts` mirrors is unchanged.** The
U+FFFC undefined-marker JSON codec (`jsonStringWithUndefined` /
`jsonParseWithUndefined`) is still present in the 9.5.1 synchronizer dists and
still **not exported publicly** — it appears in no `.d.ts` on the public type
surface (checked `@types/` across the package). Issue #52's upstream proposal
(export the pair, or document the failure class) remains valid against 9.5.1.

**Stamp format**: unchanged — the empirical round-trips in §3 produced
identical stamp-tree JSON through an unwrapped 9.5.1 store, including the
encoded-undefined deletion stamps, so `encodeUndefined`/`decodeUndefined`
round-trip cleanly on 9.5.1 and sealed archives restore unchanged.

**New validation, all favorable to this codebase** (v9.3.0 notes):

- "MergeableStore now atomically rejects HLCs that are not exactly 16
  characters or are over five minutes in the future, carries overflowing
  24-bit counters into wall-clock time, and verifies local stamps without
  mutating rejected caller payloads." Archived stamps are 16-char, past-dated
  HLCs — restores are unaffected; garbage or forged future stamps now get
  refused instead of merged.
- "String Cells, Values, and schema defaults using TinyBase's reserved leading
  U+FFFD or exact U+FFFC encodings are rejected, while invalid or
  schema-incompatible persisted encodings are ignored safely." Verified
  empirically (scratchpad `reserved.mjs`): on 9.2.0 a cell whose entire value
  is `'￼'` (U+FFFC) is **accepted** (the codec's documented ambiguity was
  real), and a string starting with U+FFFD **throws a JSON parse error from
  inside the store**; on 9.5.1 both writes are silently refused, and interior
  occurrences of either character remain accepted. After the bump the codec's
  marker is unambiguous *by construction* — the one collision case can no
  longer exist in a store. (Edge to know: a message whose text begins with the
  mojibake character `�` would be refused as a cell after the bump.)
- U+2028/U+2029 in cell text: accepted in-store on both versions, and after
  9.3.0 they also survive the wire (§2) — under 9.2.0 they were the
  fragmenter's casualty.
- Errors are now `new Error('tinybase:<code>[:detail]')` with numeric codes
  (9.5.1 dist, `errorNew`; codes documented in the
  [Error Codes guide](https://tinybase.org/guides/error-codes/)). `e.name`
  stays `'Error'`, so `restoreContent`'s report-the-class-never-the-message
  discipline (`sync/src/do.ts`) is unaffected — and upstream messages now leak
  less content, which is the direction this house wants. No code in the repo
  matches on tinybase error message text (grepped).

**API semantics**: `getMergeableContent`/`setMergeableContent` signatures and
result shapes are unchanged between the two versions' type declarations.

## 5. Durable Object SQLite persister: the bump is non-breaking for stored data

**The highest-stakes answer: for this repo's configuration, the on-disk layout
is byte-identical between 9.2.0 and 9.5.1.** Extracted from both installed
dists (`persisters/persister-durable-object-sql-storage/index.js`):

- Fragmented-mode table names: `${tablePrefix}tinybase_tables` and
  `${tablePrefix}tinybase_values` in both versions.
- CREATE TABLE schemas identical in both: tables
  `(type, table_id, row_id, cell_id, value_data, timestamp, hash)` with
  `PRIMARY KEY (type, table_id, row_id, cell_id)`; values
  `(value_id, value_data, timestamp, hash)`.
- INSERT statements identical in both.

The v9.4.0 note that flagged this question — "Fragmented Durable Object SQL
storage now encodes unsafe and uppercase prefixes collision-free. Previous
ambiguous table names are not adopted automatically and must be migrated
explicitly." — applies only to a **custom `storagePrefix`**. 9.2.0 sanitized a
prefix with `.replace(/[^a-zA-Z0-9_]/g, '_')` (collision-prone); 9.5.1 uses a
prefix verbatim only if it matches `/^[a-z0-9_]*$/` and otherwise encodes it as
`$tinybase$<hex>$`. `sync/src/do.ts:247` passes `{mode: 'fragmented'}` with
**no** `storagePrefix`, so the prefix is the empty string, which passes the
verbatim test in 9.5.1 and produced no prefix in 9.2.0 — same table names,
same columns, same rows. **A 9.2 → 9.5 bump reads the existing DO's stored
record as-is. No migration.** (9.3.0 additionally fixed "Durable Object SQL
preserves empty Ids and safely quotes generated table names" — a
read/write-correctness fix, not a layout change.)

One behavioral note for the restore road: 9.3.0's "failed transactions now
rollback" and persister-lifecycle hardening ("Persister operations now await
queued work"; "Durable Object KV persistence batches limit-safe writes
transactionally") tighten semantics under the persister but do not change
`persister.save()`'s contract that `restoreContent` relies on.

## 6. Call-site compatibility audit (every tinybase import in the repo)

Import sites: `app/src/lib/store.ts`, `connection.ts`, `tail.ts`,
`debug-sync.ts`, `store.test.ts`; `shared/schema.ts`; `sync/src/do.ts`,
`reads.ts`. No tinybase UI packages are imported anywhere, so the entire
Solid/Svelte/React "breaking-ish" surface of 9.3.0 is moot here.

- `createWsSynchronizer(store, ws, 60, undefined, undefined, onErr, FRAGMENT_SIZE)`
  (`app/src/lib/store.ts:295`): the 9.3.0 multiplex form is a separate
  **overload** selected by a string `channelId` third argument
  (`@types/synchronizers/synchronizer-ws-client/index.d.ts`, "@since v9.3.0");
  the legacy 7-arg signature is declared unchanged in 9.5.1. A numeric third
  argument keeps the legacy path. No change needed.
- `createOpfsPersister` (`store.ts:77`): exported unchanged from
  `persisters/persister-browser` in 9.5.1 (same three exports in both
  versions' `.d.ts`). 9.3.0 hardened it: "OPFS always closes successful writes
  and aborts failed ones" — strictly good; the known logout race documented in
  `connection.ts` (no drain to await) is a different gap and is not addressed.
- `createMiddleware` + all five guard callbacks used in `do.ts`
  (`addWillSetCellCallback`, `addWillSetValueCallback`,
  `addWillDelValueCallback`, `addWillDelValuesCallback`,
  `addWillApplyChangesCallback`): the middleware API surface is **identical**
  between the two versions' `.d.ts`. One semantic note: 9.3.0's "Middleware
  receives cloned object and array values in public JavaScript form" means the
  size-guard's `cellJsonBytes` measures the same public form it did before
  (arrays were already public-form in the callback in 9.2.0); cloning only
  protects against mutation. Guards compile and behave as written.
- `WsServerDurableObject` subclass (`do.ts`): all overridden members
  (`createPersister`, `getFragmentSize`, `fetch`, `webSocketMessage`,
  `webSocketClose`, `alarm`, `getPathId`, `getWebSockets` usage) exist
  unchanged. 9.3.0: "WsServerDurableObject reports an empty path before its
  first connection" — `do.ts` already treats `''` as owner-unavailable
  (`ownerAvailable`), so this is handled.
- `getHash` (`store.ts`, `do.ts`): exported unchanged; hash values for
  identical input are unchanged (the §3 repros reproduced source content
  hashes across versions).
- `createMergeableStore().setSchema(...)` (`shared/schema.ts`): unchanged;
  schema *objects* are now cloned before normalization (9.3.0), so the
  `as const` frozen schemas remain safe (they were working anyway).

**Behavior changes to absorb consciously** (no code change, but new refusals):
under 9.3.0+ the store rejects writes it used to accept — strings that are
exactly U+FFFC or lead with U+FFFD (§4), unserializable rich content, HLCs
malformed or >5 min future. All are refusals of data this record should never
contain; the cell-size guard and schema already refuse far more.

## 7. New capabilities worth knowing about

- **`onIgnoredError` on `WsServerDurableObject`** (v9.3.0; in the 9.5.1
  `.d.ts`: "called when the Durable Object receives an invalid synchronization
  protocol message. The sending client is disconnected after this method is
  called"). Directly useful: `JulianSyncDO` currently has no visibility into
  malformed-traffic disconnects; overriding this would let the DO ledger them
  the way it ledgers refusals.
- **Schema enums and type unions** (v9.5.x): `messages.role`
  (`'user'|'assistant'|'system'`), `messages.kind` (`'chat'|'system'|'compact'`),
  and `jobs.status` (`'open'|'taken'|'closed'|'withdrawn'`) are exactly the
  shape `{enum: [...]}` was built for, and the schema-aware types would then
  infer the unions. Caveat before adopting: an enum turns any out-of-enum
  value already in the record into a rejected write/load — audit the annexed
  Fireproof rows' actual `role`/`kind` values first, and remember the schema
  is applied on both the client and the DO.
- **WebSocket multiplexing** (v9.3.0): not applicable to the DO server (one
  path/DO per socket, per the release note), but if the app ever runs a second
  MergeableStore (e.g. a separate presence or drafts store), one physical
  socket could carry both — with the release note's own warning that "Channel
  Ids are not an authorization boundary," which matters in a gate-shaped house.
- **`selectAll` queries** (v9.4.0): relevant only if the read verbs
  (`sync/src/reads.ts`) or the app ever adopt the Queries module; today's
  reads are hand-rolled over the store and gain nothing automatically.
- **`jsonStringWithUndefined` / `jsonParseWithUndefined`: still internal.**
  Present in the 9.5.1 synchronizer bundles, absent from every public `.d.ts`.
  Issue #52's proposal (export the pair or document the lossy-JSON gotcha) is
  still unaddressed upstream and still worth carrying.
- **Coming, not in range**: 9.6.0-beta.1 (2026-08-19) adds "MergeableStore
  support for IndexedDB" plus new Persisters (PostgreSQL/pg, Supabase,
  better-sqlite3, Capacitor) per the release listing. When 9.6.0 lands, the
  OPFS-only rationale in `app/src/lib/store.ts` ("TinyBase's IndexedDB
  persister supports plain Stores only") will need re-evaluation — IndexedDB
  with stamps would lift the FileSystemObserver/Chrome-only constraint noted
  there.

## 8. Bump verdict and checklist

The bump 9.2.0 → 9.5.1 is **low-risk and worth taking**:

- DO stored data: no layout change for this config (§5). The canonical record
  is safe; no migration, no dual-version window needed beyond ordinary care.
- Wire protocol: back-compatible (legacy signature and wire retained, §2, §6);
  a 9.2 client can talk to a 9.5 server and vice versa during a rolling
  deploy, though the fragmenter fix only protects legs where *both* ends are
  upgraded senders of their own fragments (each side fragments what it sends).
- The #53 hazard is unchanged — keep the lazy guards and the pinned test (§3).
- The export codec and sealed archives are unaffected; their assumptions get
  strictly stronger (§4).
- What actually gets fixed by bumping: the U+2028/U+2029-eating fragmenter
  (§2), the `FRAGMENT_SIZE` bytes-vs-chars ambiguity at Cloudflare's 1 MiB cap
  (§2), the leading-U+FFFD in-store throw (§4), plus the broad 9.3.0
  transaction-rollback and persister-lifecycle hardening.

Checklist for the bump PR:
1. Pin `^9.5.1` in `app/`, `shared/`, `sync/` (and reconcile the root's
   `^9.3.0` — three workspaces and the root currently disagree).
2. Run the full suites; `sync/test/restore.test.ts` must stay green with its
   array-cell fixture (it will — §3 verified the behavior is identical).
3. Eyeball one live first-sync and one export hash against a pre-bump export
   (stamps and hashes are unchanged, §4 — this is a confirmation, not a fear).
4. Optional, same PR or next: override `onIgnoredError` in `JulianSyncDO` for
   malformed-traffic visibility (§7).
5. Leave #53 open with a note that 9.5.1 still reproduces it (this file, §3);
   #52 likewise still valid.
